# Интерактивный веб-дашборд для AI-агентов: исследование лучших практик

> Статус: завершено · Дата: 2026-07-27 · Автор: AI-исследование

## Краткое резюме (ключевые рекомендации)

1. **Перейти с polling на SSE (Server-Sent Events)** — самый простой путь к realtime без
   зависимостей: `EventSource` встроен в браузер, сервер отдаёт `text/event-stream`.
   Для vanilla JS это идеальный компромисс: проще WebSocket, быстрее polling.

2. **Внедрить «Grid View» (матрицу статусов)** — главная находка из Airflow UI:
   строки = задачи, колонки = запуски, цвет = статус. Компактная визуализация истории
   на одном экране без скролла.

3. **Добавить streaming-лог с автоскроллом и поиском** — сейчас лог показывается
   статично. Живой `tail -f` с ANSI-цветами, виртуальным скроллом и кнопкой
   «follow/jump to bottom» радикально улучшит отладку.

4. **Клавиатурные shortcuts для power-user действий** — `r` = retry, `k` = kill,
   `Esc` = закрыть панель, `/` = фокус в поиск, `⌘+K` = командная палитра.
   Экономит секунды при каждом действии.

5. **Сохранять состояние при автообновлении** — не сбрасывать скролл, не закрывать
   открытую панель, не терять фильтры. Инкрементальный diff-update DOM вместо
   полной перерисовки.

6. **Dark mode как first-class citizen** — в проекте уже есть `prefers-color-scheme`,
   добавить явный тогл-переключатель (солнце/луна) с сохранением в `localStorage`.

7. **URL-state для шаринга** — фильтры, сортировка, выбранная задача — в `location.hash`.
   Позволяет скинуть коллеге ссылку «посмотри вот эту упавшую задачу».

## 1. UI-паттерны job/task queue дашбордов

Изучены пять зрелых инструментов мониторинга фоновых задач. Вот что делает их
удобными — и что применимо к нашему `.ai` дашборду.

### 1.1 Bull Board (Bull/BullMQ) — [github.com/felixmosh/bull-board](https://github.com/felixmosh/bull-board)

**Ключевые фичи:**
- **Обзор очередей** — на одном экране все очереди с количеством waiting/active/completed/failed
- **Таблица задач** с фильтрацией по статусу и поиском по ID/данным
- **Детализация задачи**: data, opts, return value, stacktrace, логи
- **Действия**: retry, clean, remove, promote (переместить в начало очереди)
- **Исторические метрики** (опциональный пакет `@bull-board/metrics`): графики
  throughput (completed/failed per minute), 7/30/90-дневная ретроспектива
- **Read-only режим** для продакшена

**Что взять:**
- Фильтр по статусу + текстовый поиск уже есть у нас. Не хватает **массовых действий**
  (retry всех failed, clean всех завершённых) — Bull Board показывает это в header'е
  очереди кнопками.
- **График throughput** (завершено/упало за последний час) — в нашей «Статистике»
  можно добавить временной график, сейчас там только aggregated counters.
- Retry **одной кнопкой** из строки таблицы — у нас сейчас нужно открыть detail-панель
  и нажать отдельную кнопку.

### 1.2 Flower (Celery) — [flower.readthedocs.io](https://flower.readthedocs.io/en/latest/)

**Ключевые фичи:**
- **Realtime-мониторинг workers и задач** — автообновление без перезагрузки страницы
- **Фильтрация задач** по состоянию, worker'у, типу, временному диапазону
- **Статистика worker pool** — сколько процессов/тредов, загрузка
- **Детали задачи**: args, kwargs, result, traceback, временные метки каждого этапа
- **Prometheus-интеграция** и готовый Grafana-дашборд для долгосрочной аналитики
- **Действия**: rate limit, revoke (отмена), таймаут задач

**Что взять:**
- **Временные метки этапов** задачи: queued_at → started_at → finished_at. В нашем
  `job.json` эти поля уже есть — можно визуализировать как мини-диаграмму Ганта
  в строке таблицы.
- **Rate limiting / throttle** — пока не актуально, но если агентов станет больше 3-5,
  пригодится.

### 1.3 Airflow 3.0 UI — [airflow.apache.org/docs/stable/ui.html](https://airflow.apache.org/docs/apache-airflow/stable/ui.html)

**Самая богатая эталонная реализация.** Ключевые находки:

**Grid View (матрица статусов):**
- **Строки = задачи, колонки = запуски (DAG runs), цвет ячейки = статус**
- Позволяет на одном экране увидеть паттерн: «последние 5 запусков упали на одном
  и том же шаге»
- При наведении — tooltip с деталями, при клике — drill-down в логи
- **Это паттерн #1, который надо внедрить** — у нас сейчас плоская таблица,
  а матрица гораздо информативнее

**Graph View (топология зависимостей):**
- Для нас менее актуально (у нас задачи независимы), но если появятся
  цепочки задач (job A → job B), этот паттерн станет критичным

**Tabbed detail view:**
- Для одной задачи: Logs / Rendered Templates / XCom / Events / Code / Details
- У нас уже есть похожая деталь-панель, но всё свалено в один скролл.
  Табы улучшат навигацию: «Лог» / «Result.md» / «prompt.md» / «Диагностика»

**Фильтры + поиск:**
- **Advanced search (⌘+K)** — command palette для быстрого перехода к задаче
  по ID или имени. Прямой analog Spotlight/CMD+K в IDE.

**Тёмная/светлая тема:**
- Airflow 3 использует `oklch()` и `color-mix()` — современные CSS-функции.
- Переключатель темы в bottom corner, не в настройках. Сохраняется в user prefs.

**Домашняя страница:**
- Health indicators компонентов системы (Scheduler, Triggerer, DB)
- Quick links по статусам («Failed Dags», «Running Dags»)
- График истории запусков

**Что взять:**
- **Grid View** — приоритет #1
- **⌘+K command palette** — приоритет #2
- **Табы в detail-панели** — приоритет #3
- **Health indicators** — если добавим мониторинг самого orchestrator

### 1.4 Temporal Web UI — [docs.temporal.io/web-ui](https://docs.temporal.io/web-ui)

**Ключевые фичи:**
- **Namespace switcher** — переключение между изолированными окружениями
  (для нас — между проектами/репозиториями, где запущен `.ai`)
- **Saved Views** (сохранённые фильтры) — до 20 пользовательских пресетов
  фильтров. Хранятся локально в браузере. Можно делиться через URL.
- **Workflow History**: четыре представления — Timeline (хронологический),
  All (все события), Compact (логические группы), JSON (сырые данные)
- **Input/Results**: встроенный просмотр аргументов и возвращаемых значений
- **Call Stack**: живой stack trace выполняющегося workflow
- **Relationships**: дерево parent/child workflows
- **Действия**: Cancel, Signal, Reset, Terminate, «Start Workflow Like This One»
  (перезапуск с теми же параметрами)

**Что взять:**
- **Saved Views** — супер-полезно: «хочу видеть только failed задачи за сегодня»
  → сохранить как «Today's failures». Реализуется через `localStorage` + фильтры.
- **Несколько представлений истории**: для нас это может быть «Сырой JSON job.json» +
  «Человекочитаемое» + «Только события» (created/started/finished/healed).
- **«Start Like This One»** — запуск новой задачи с теми же параметрами
  (task, capability, prompt). Прямо из detail-панели.

### 1.5 GitHub Actions UI — [docs.github.com/.../using-the-visualization-graph](https://docs.github.com/en/actions/monitoring-and-troubleshooting-workflows/using-the-visualization-graph)

**Ключевые фичи:**

## 2. Realtime-обновление: Polling vs WebSocket vs SSE

### 2.1 Сравнительная таблица

| Критерий | Polling (fetch) | SSE (EventSource) | WebSocket |
|---|---|---|---|
| **Направление** | Client → Server → Client | Server → Client | ↔ Bidirectional |
| **Протокол** | HTTP (request/response) | HTTP (long-lived stream) | WS (upgrade) |
| **Сложность сервера** | Минимальная | Низкая | Средняя |
| **Сложность клиента** | Минимальная (`fetch` + таймер) | Минимальная (`EventSource`) | Средняя (библиотека или ручной `WebSocket`) |
| **Auto-reconnect** | Ручной | Встроен в браузер | Ручной |
| **Proxy/LB совместимость** | Полная | Полная (это HTTP) | Может требовать настройки |
| **Задержка** | Равна интервалу poll | Мгновенно (стрим) | Мгновенно |
| **Расход батареи/трафика** | Высокий (даже если нет изменений) | Низкий (только при событиях) | Низкий |
| **Лимит соединений** | Нет (каждый запрос новый) | HTTP/1.1: 6 на домен; HTTP/2: 100 streams | Нет практических ограничений |
| **Совместимость с vanilla JS** | `fetch()` | `new EventSource(url)` — встроен | `new WebSocket(url)` — встроен |

### 2.2 Детальный анализ

#### Polling (текущее решение)

**Как работает сейчас** в `dashboard.html`: клиент вызывает `setInterval(loadJobs, N)`,
сервер читает файлы с диска и возвращает JSON.

**Плюсы:**
- Предельно прост: `fetch()` + `setInterval()` — 3 строки кода
- Совместимость со всем: любой сервер, любой прокси, любой браузер
- Нет долгоживущих соединений — сервер не держит сокеты

**Минусы:**
- **Задержка = интервал опроса.** Если интервал 5 секунд, статус меняется
  с задержкой до 5 секунд. Для running-задач это ощутимо.
- **Пустая трата ресурсов:** каждый poll читает все job.json с диска, даже если
  ни одна задача не изменилась.
- **Сложно масштабировать:** при 50+ задачах каждый poll читает 50 файлов.
- **Thundering herd:** несколько открытых вкладок → N × запросов к серверу.

#### SSE (Server-Sent Events) — **рекомендуется для этого проекта**

**Как работает:** сервер устанавливает долгоживущее HTTP-соединение, шлёт
`text/event-stream`. Браузер получает данные через `EventSource` API.

**Клиент (vanilla JS, ноль зависимостей):**
```javascript
const es = new EventSource('/api/events');
es.addEventListener('job-update', (e) => {
  const job = JSON.parse(e.data);
  updateJobRow(job);  // инкрементальный update одной строки
});
es.addEventListener('job-new', (e) => { /* ... */ });
```

**Сервер (Node.js без Express):**
```javascript
// Установка соединения
res.writeHead(200, {
  'Content-Type': 'text/event-stream',
  'Cache-Control': 'no-cache',
  'Connection': 'keep-alive',
});
res.write(':ok\n\n');  // comment-строка — keep-alive

// Отправка события
res.write(`event: job-update\ndata: ${JSON.stringify(job)}\n\n`);
```

**Ключевые особенности (из MDN):**
- **Автопереподключение** встроено в браузер: при обрыве соединения `EventSource`
  сам переподключится. Сервер может отправить `id:` для возобновления с последнего
  полученного события (поле `Last-Event-Id` в заголовке переподключения).
- **Именованные события:** `event: job-update` vs `event: job-new` — разные
  обработчики на клиенте (`addEventListener`). Можно слать события разного типа
  по одному соединению.
- **Keep-alive:** сервер периодически шлёт строки, начинающиеся с `:` (комментарии
  в протоколе SSE) — это предотвращает таймаут соединения.
- **Лимит HTTP/1.1:** 6 соединений на браузер+домен. Для одного дашборда хватает
  (1 SSE-соединение). Но если пользователь откроет 6+ вкладок — упрётся в лимит.
  Решение: использовать HTTP/2 (100 параллельных streams) или закрывать SSE
  на неактивных вкладках через `document.visibilitychange`.

**Почему SSE идеален для этого проекта:**
1. Данные текут только в одну сторону (сервер → клиент). Клиенту не нужно
   отправлять realtime-данные (действия вроде retry/kill — это обычные POST).
2. `EventSource` — часть Web API, доступен без полифилов во всех современных
   браузерах с 2017 года.
3. Серверная реализация на чистом Node.js — 15 строк кода.
4. Можно слать инкрементальные обновления: только изменившиеся поля задачи,
   а не весь список заново.

**Как внедрить в наш сервер (`dashboard.js`):**
- Добавить endpoint `/api/events`
- При старте соединения — отправить `event: init` со всеми текущими задачами
- При изменениях (новая задача, смена статуса) — `event: job-update` с одной задачей
- На клиенте — заменить `setInterval(loadJobs)` на инкрементальный update строк
- Для обратной совместимости — оставить polling как fallback (если SSE не подключился)

#### WebSocket

**Плюсы:**
- Полнодуплексный: клиент может слать данные (потенциально — live-ввод команд)
- Нет лимита соединений
- Бинарные данные

**Минусы для этого проекта:**
- **Избыточен:** не нужен bidirectional канал. Все действия пользователя (retry, kill)
  — это POST-запросы, им не нужен WebSocket.
- **Сложнее в реализации:** нужно обрабатывать upgrade handshake, ping/pong,
  переподключение.
- **Прокси:** некоторые corporate прокси блокируют WebSocket upgrade.
- На чистом Node.js без библиотек — больше кода, чем SSE.

**Когда WebSocket станет нужен:** если появится функционал live-терминала в браузере
(ввод команд агенту в реальном времени), collaborative-фичи (несколько операторов
видят один дашборд) или streaming бинарных данных.

### 2.3 Рекомендация

**Внедрить SSE как основной транспорт, polling как fallback:**

```
1. Клиент пробует EventSource('/api/events')
2. Если за 2 секунды нет соединения → fallback на setInterval(fetch, 3s)
3. При успешном SSE:
   - init-событие отдаёт все текущие задачи
   - последующие события — только дельты (изменённые задачи)
   - рендеринг — инкрементальный DOM-update, не полная перерисовка
```

Ссылки:
- [MDN: Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)
- [WHATWG HTML Spec: Server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html)

## 3. Интерактивные виджеты

### 3.1 Streaming Log Viewer

Сейчас лог показывается как статичный `<pre>` в detail-панели. Для живой задачи
(статус `running`) критически важно видеть лог в реальном времени.

**Что должно быть в идеальном log viewer (паттерны из CI/CD тулов):**

1. **Автоскролл (follow mode):**
   - По умолчанию скролл приклеен к низу — новые строки появляются, скролл
     уезжает вниз (как `tail -f`)
   - Если пользователь прокрутил вверх — автоскролл отключается. Кнопка
     «Follow» / «Jump to bottom» возвращает его
   - Индикатор: цветная полоска или иконка, показывающая режим follow

2. **Виртуальный скролл:**
   - Если лог 10 000+ строк, рендерить все в DOM — убить производительность
   - Виртуализация: в DOM только видимые строки (50-100), остальное —
     placeholder с корректной высотой скроллбара
   - **Проблема для vanilla JS:** нужна библиотека или своя реализация
     (жизнеспособно: десятки туториалов, ~100 строк кода на `IntersectionObserver`)
   - **Альтернатива для начала:** `max-height` + `overflow-y: auto` + лимит
     на количество строк (последние 5000). Для небольшого числа задач хватит.

3. **ANSI-цвета:**
   - Вывод AI-агентов часто содержит ANSI escape-коды (цвета, bold)
   - Нужно либо парсить ANSI → HTML spans, либо использовать `<pre>` с `white-space: pre-wrap`
   - Лёгкая альтернатива: CSS-правила для подсветки ключевых слов (ERROR, WARN, PASSED)

4. **Поиск по логу:**
   - `Ctrl+F` браузера работает только в видимом DOM
   - Нужен свой поиск: поле ввода, подсветка найденного, навигация
     по совпадениям (Enter — следующее, Shift+Enter — предыдущее)

5. **Line numbers:**
   - Помогают при обсуждении: «смотри строку 1423 в логе»
   - Нумерация в отдельной колонке (monospace, muted color)

6. **Копирование:**
   - Кнопка «Copy log» — копирует весь лог в буфер обмена
   - «Copy selection» — стандартный браузерный selection

**Для реализации в vanilla JS без фреймворков:**
- Лог хранить как массив строк в памяти (а не как один HTML-блок)
- При добавлении новых строк — `appendChild` в конец pre-элемента
- Для виртуализации — использовать `IntersectionObserver` + пустые div'ы-плейсхолдеры
- Альтернатива: отдавать лог чанками через SSE (`event: log-chunk`)

### 3.2 Графики и статистика

**Что уже есть в дашборде (секция «Статистика»):**
- Карточки с агрегированными числами (total/completed/failed/tokens/cost)
- Простая bar-диаграмма (CSS div'ы разной высоты) — распределение по дням
- Разбивка по моделям (runner/model)

**Что можно улучшить без external-библиотек:**

1. **Временной график активности (throughput over time):**
   - X = время (последние 24 часа с шагом 1 час), Y = количество задач
   - Два ряда: completed (зелёный), failed (красный)
   - Реализация на `<canvas>` с минимальным кодом (~50 строк)
   - Или даже CSS-only вариант как сейчас, но с подписями оси X

2. **График стоимости (cost over time):**
   - Кумулятивная стоимость за период
   - Разбивка по моделям — stacked bar

3. **График длительности (duration distribution):**
   - Histogram: сколько задач заняло <10с, 10-30с, 30-60с, 1-5мин, >5мин
   - Помогает понять, не деградирует ли производительность

4. **Timeline задач (swimlane/Gantt):**
   - Горизонтальные полосы — задачи, ось X — время
   - Цвет полосы — статус (зелёный = completed, красный = failed)
   - Ширина полосы — длительность выполнения
   - Позволяет увидеть параллельность: какие задачи шли одновременно
   - **Отличный виджет для нашей «Статистики»** — визуализирует загрузку агентов

**Для vanilla JS без библиотек:**
- Простые графики — CSS div'ы (как уже сделано для распределения по дням)
- Timeline — `<canvas>` с ручной отрисовкой (~100 строк кода)
- Как fallback — простые числа и таблицы работают отлично, не надо переусложнять

### 3.3 Gantt-подобный индикатор в строке таблицы

В Airflow каждая задача в списке имеет мини-диаграмму Ганта — горизонтальную полоску,
показывающую start/end/duration. Для компактного дашборда это даёт много информации
без открытия detail-панели.

**Реализация:** в дополнительной колонке таблицы — горизонтальный bar, ширина
которого пропорциональна `duration / maxDuration`. Цвет — статус. При наведении —
точные цифры в tooltip.

## 4. UX best practices для dev-tools дашбордов

### 4.1 Информационная плотность

**Правило для dev-tools (не для consumer):** разработчикам и операторам нужно
**много данных на одном экране**. Они готовы к более высокой плотности, чем
обычные пользователи.

**Что это значит для нас:**
- Таблица должна быть компактной: `font-size: 12-13px`, `padding: 4-6px` — у нас уже так
- Использовать моноширинный шрифт для технических данных (ID, хеши, пути)
- Сокращать длинные строки с `text-overflow: ellipsis` + tooltip при наведении
- **Не прятать важное за клики** — статус, время, стоимость должны быть видны
  в таблице без открытия detail-панели
- Колонки с возможностью show/hide (сейчас все колонки фиксированы)

### 4.2 Клавиатурные сокращения (keyboard shortcuts)

**Обязательный минимум:**

| Клавиша | Действие |
|---|---|
| `/` | Фокус в поле поиска |
| `⌘+K` / `Ctrl+K` | Command palette: поиск задачи по ID или имени, быстрый переход |
| `Esc` | Закрыть detail-панель / модальное окно / выйти из поиска |
| `j` / `k` | Навигация вниз/вверх по таблице (vim-style) |
| `Enter` | Открыть detail выделенной задачи |
| `r` | Retry выделенной задачи |
| `x` | Kill выделенной задачи |
| `?` | Показать/скрыть шпаргалку со всеми shortcuts |

**Реализация в vanilla JS:** глобальный `keydown` listener с `event.key` + проверка,
что фокус не в input/textarea (кроме `/`).

### 4.3 Dark mode

**Текущее состояние:** используется `@media (prefers-color-scheme: dark)` —
автоматическое переключение на системные настройки. Это хорошо, но недостаточно.

**Что добавить:**
- **Ручной переключатель** (солнце ☀ / луна 🌙) в header
- Три состояния: Light / Dark / Auto (system)
- Сохранение выбора в `localStorage`
- При загрузке страницы: localStorage > system preference > light

**Зачем:** разработчики часто работают в тёмной теме IDE, но светлой ОС
(или наоборот). Ручной оверрайд обязателен.

### 4.4 Сохранение состояния при автообновлении

**Критическая проблема любого автообновляющегося дашборда:** если перерисовать весь
DOM, пользователь теряет:
- Позицию скролла
- Открытую detail-панель
- Выделенную строку
- Введённый текст в поиске (если не debounced)
- Раскрытые секции

**Решение — инкрементальные обновления:**
1. Вместо `main.innerHTML = newHTML` делать targeted updates:
   - Новая задача → `tbody.appendChild(newRow)`
   - Изменился статус → обновить только status-ячейку и время
   - Задача исчезла (удалена) → `row.remove()`
2. Для этого нужен **diff** между старым и новым состоянием
3. SSE-события должны нести только изменившиеся поля (дельта), а не весь объект

**Упрощённый вариант без диффа (для начала):**
- Если открыта detail-панель — не перерисовывать её содержимое
- Сохранять `scrollTop` таблицы, восстанавливать после ререндера
- Сохранять выделенную строку (data attribute), восстанавливать `class` после ререндера

### 4.5 URL-state (шаринг)

**Сейчас:** при открытии дашборда всегда показывается дефолтное состояние.
Невозможно скинуть ссылку «посмотри задачу abc123».

**Что добавить:**
- Фильтры в `location.hash`: `#status=failed&model=deepseek`
- Выбранная задача: `#job=abc123`
- Сортировка: `#sort=createdAt&dir=-1`
- Активная вкладка: `#tab=stats`

**Реализация:** `window.onhashchange` + чтение при загрузке. `URLSearchParams` для
парсинга (или ручной парсинг `location.hash.slice(1)`).

### 4.6 Действия и обратная связь

**Паттерны из изученных тулов:**
- **Действия в строке таблицы** (не только в detail-панели): иконки retry/kill
  справа в строке. Экономит клик.
- **Массовые действия:** «Retry all failed», «Clean completed» — кнопка над таблицей.
- **Подтверждение опасных действий:** kill, delete — модальное окно или undo toast.
  Не делать необратимые действия по одному клику.
- **Toast-уведомления** (уже есть) — показывать результат действия:
  «Задача abc123 отправлена на retry» / «Ошибка: не удалось kill задачу»
- **Loading state кнопок:** после клика кнопка становится disabled + спиннер
  до получения ответа от сервера. Предотвращает double-click.

### 4.7 Фильтрация и поиск

**Что улучшить относительно текущего состояния:**
- **Debounced search:** ввод текста → ждать 300ms после последней клавиши → фильтровать.
  Сейчас (судя по коду) фильтрация происходит по `value` поля при рендере — это ок,
  но при большом числе задач может тормозить. Debounce + фильтрация в памяти,
  не на DOM.
- **Чипсы активных фильтров:** под строкой поиска показывать «Status: failed ✕»
  «Model: deepseek ✕» — видно, какие фильтры активны, можно снять по одному.
- **Сохранение фильтров в URL** (см. выше) + восстановление при открытии.

### 4.8 Пустая страница и краевые случаи

Часто забывают, но важно для первого впечатления:
- **Нет задач:** показать не пустую таблицу, а сообщение «Нет задач. Запустите
  первую через `agent delegate ...`» с примером команды.
- **Нет задач по фильтру:** «По фильтру 'failed' задач не найдено. Очистить фильтр?»
- **Ошибка загрузки:** не молча падать, показать баннер с ошибкой и кнопкой «Retry».

## 5. Конкретные рекомендации для `.ai` дашборда

С учётом ограничений проекта (vanilla HTML/JS, один файл, Node.js без фреймворков,
нет build-системы, ноль зависимостей):

### 5.1 Этап 1: быстрые победы (MVP улучшений, ~2-4 часа)

1. **Переход на SSE** (файл `lib/dashboard.js`):
   - Endpoint `GET /api/events`
   - Сервер: при изменении задачи (статус сменился) — отправить `event: job-update`
   - Клиент: заменить `setInterval(loadJobs, ...)` на инкрементальные DOM-update
   - Fallback на polling при ошибке SSE

2. **Клавиатурные shortcuts** (файл `lib/dashboard.html`, секция `<script>`):
   - `Esc` → закрыть панель
   - `r` → retry выделенной задачи
   - `/` → фокус в поиск
   - `?` → показать шпаргалку

3. **Ручной переключатель темы** (CSS + JS):
   - Тогл в header: ☀ / 🌙
   - `localStorage` для сохранения
   - Три состояния: auto / light / dark

### 5.2 Этап 2: структурные улучшения (~1-2 дня)

4. **Табы в detail-панели:**
   - «Обзор» (статус, время, стоимость, модель)
   - «Лог» (stderr.log — streaming для running-задач)
   - «Результат» (result.md, verify.log)
   - «prompt.md»
   - «job.json» (raw JSON для отладки)

5. **URL-state:**
   - `location.hash` с фильтрами и выбранной задачей
   - Восстановление при загрузке
   - Кнопка «Copy link» в detail-панели

6. **Действия в строке таблицы:**
   - Иконки retry/kill (без открытия detail-панели)
   - Массовая кнопка «Retry all failed» над таблицей

### 5.3 Этап 3: продвинутые виджеты (~2-3 дня)

7. **Grid View** — альтернативное представление таблицы:
   - Строки = задачи, колонки = запуски (последние N)
   - Цвет ячейки = статус
   - Переключение: кнопка «Таблица» / «Сетка»

8. **Timeline задач** в секции «Статистика»:
   - Горизонтальные полосы задач на оси времени
   - Визуализация параллельности

9. **Streaming log viewer:**
   - Follow mode для running-задач
   - Line numbers
   - Кнопка «Copy log»

### 5.4 Что НЕ стоит делать (anti-рекомендации)

- **Не внедрять WebSocket** — избыточен, пока нет bidirectional realtime-потребностей
- **Не добавлять React/Vue/Svelte** — проект нарочно минималистичный. Vanilla JS
  с инкрементальными DOM-обновлениями покрывает все потребности дашборда.
- **Не строить сложные графики с библиотеками** (D3, Chart.js) — CSS + canvas
  + простые бары покрывают 90% потребностей. Библиотека = зависимость = усложнение
  деплоя.
- **Не делать realtime-обновление графика** для «Статистики» — там данные
  исторические, достаточно рефрешить при переключении на вкладку.
- **Не прятать действия в контекстное меню как единственный способ** —
  правая кнопка мыши ≠ discoverable. Основные действия должны быть видны.
- **Не использовать `<iframe>` для лога** — сложно стилизовать, проблемы
  с автоскроллом.

## Текстовое резюме

Проведено исследование лучших практик построения интерактивных дашбордов для
мониторинга фоновых задач на основе пяти зрелых инструментов (Bull Board, Flower,
Airflow 3.0, Temporal, GitHub Actions) и best practices по realtime-транспорту,
UX для dev-инструментов и визуализации логов.

**Главный вывод:** текущий дашборд `.ai` (файлы `lib/dashboard.html` и
`lib/dashboard.js`) — добротная база, но ему не хватает трёх вещей для
качественного скачка в UX:

1. **Realtime-обновлений** — переход с polling на SSE (`EventSource` API)
   даст мгновенное отображение смены статуса без постоянного перечитывания
   файлов с диска. Для vanilla JS это 15 строк серверного кода и 10 строк
   клиентского. Браузерный `EventSource` сам обрабатывает переподключения.

2. **Grid View (матрицы статусов)** — самая яркая находка из Airflow UI.
   На одном экране без скролла показывает статус всех последних запусков
   всех задач в виде цветовой сетки. Мгновенно видны проблемные задачи.

3. **Клавиатурной навигации** — `Esc`/`r`/`j`/`k`/`/`/`⌘+K` превращают
   дашборд из «посмотреть глазами» в «работать руками». Для dev-инструмента
   это не «nice to have», а ожидаемый минимум.

Все рекомендации предполагают реализацию на **чистом vanilla HTML/JS** без
фреймворков и npm-зависимостей — в соответствии с философией проекта.
Полный список конкретных шагов разбит на три этапа в разделе 5.
