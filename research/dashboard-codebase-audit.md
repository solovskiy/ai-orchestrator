## 1. Текущая архитектура

### Общая схема

```

│ Browser │ ◄──────────────────────────► │ dashboard.js  │
```

### Клиентская часть (`lib/dashboard.html`)

Весь HTML, CSS и JavaScript живут в одном файле — inline-стили
(строки 8–97) и inline-скрипты (строки 119–649). Ни внешних CSS, ни
модулей, ни фреймворков.

**Три вкладки (tab-based SPA):**

| Вкладка     | Функция загрузки   | API-эндпоинт     | Рендеринг                    |
|-------------|--------------------|-------------------|-----------------------------|
| Задачи      | `loadJobs()`       | `GET /api/jobs`   | Полная перерисовка строк     |
| Статистика  | `loadStats()`      | `GET /api/stats`  | Полная перерисовка карточки  |
| Агенты      | `loadSettings()`   | `GET /api/agents` | Полная перерисовка карточки  |

**Механизм обновления — polling, интервал 5 секунд** (строка 642–649):

```javascript
setInterval(() => {
  const tab = $('nav button.active')?.dataset?.tab;
  if (tab === 'settings') {
    const ed = $('#agent-editor');
    if (ed && !['', 'none'].includes(ed.style.display)) return;
  }
  (routes[tab] || loadJobs)();
}, 5000);
```

Логика: каждые 5 секунд вызывает функцию активной вкладки. Для settings
есть guard: если редактор агента открыт, перезагрузка пропускается
(исправлено в коммите `6bc683f` — раньше автообновление сносило DOM и
редактор пропадал).

**Рендеринг DOM — полная перерисовка `$('#main').innerHTML = h`**.
Фильтры, сортировка, выделение строк — всё заново на каждом вызове
`renderJobs()`, `loadStats()`, `loadSettings()`. Это значит:
- Состояние фильтра/сортировки живёт в переменных JS (`sortField`,
  `sortDir`, `jobsCache`), а значения `<input>`-фильтров считываются
  заново из DOM при каждой перерисовке — отсюда в `renderJobs()` строки
  165–167 читают `$('#filter-status')?.value`, но тут же в строке
  186–195 заново генерируют `<select>`/`<input>`-элементы, а их `value`
  прописывают через атрибут `selected`/`value`. Это работает, но хрупко.

- Открытая detail-панель (`#detail`) не сбрасывается, потому что это
  другой элемент DOM, не внутри `#main`. Но если пользователь открыл
  detail и через 5 секунд таблица перерисовалась — выделение строки
  теряется (нигде не хранится, какая строка «активна»).

- Панель редактора агента (`#agent-editor`) тоже вне `#main` — отсюда
  вышеупомянутый баг `6bc683f`.

### Серверная часть (`lib/dashboard.js`)

Чистый `http.createServer()` Node.js, ноль зависимостей. Слушает
`127.0.0.1:<port>` (по умолчанию `9191`).

**Запуск:** `agent dashboard [--port N] [--open]` → `cmd_dashboard()` в
`bin/agent` (строка 694–710) вызывает `node lib/dashboard.js`.

**Маршруты API:**

| Маршрут                          | Обработчик        | Что делает                                |
|----------------------------------|-------------------|-------------------------------------------|
| `GET /` или `/index.html`        | `serveHtml()`     | Отдаёт `lib/dashboard.html`               |
| `GET /api/jobs`                  | `apiJobs()`       | Список задач (без detail-полей)           |
| `GET /api/jobs/:id`              | `apiJobDetail()`  | Полный detail + result.md/stderr/verify   |
| `GET /api/jobs/:id/result`       | (inline)          | Только result.md как text/plain           |
| `GET /api/jobs/:id/stderr`       | (inline)          | Только stderr.log (последние 100 строк)   |
| `GET /api/stats`                 | `apiStats()`      | Агрегаты: по дням, моделям, capability    |
| `GET /api/capabilities`          | `apiCapabilities()`| Устаревшее (capabilities/*.json)          |
| `POST /api/capabilities/:name`   | `apiUpdateCapability()`| Устаревшее обновление capability       |
| `GET /api/models`                | `apiModels()`     | Список моделей (opencode + defaults)      |
| `GET /api/agents`                | `apiAgents()`     | Список агентов (v3 agents/*.json)         |
| `GET /api/agents/:name`          | `apiAgentDetail()`| Детали одного агента                      |
| `POST/PUT /api/agents/:name`     | `apiAgentSave()`  | Сохранить агента                          |
| `DELETE /api/agents/:name`       | `apiAgentDelete()`| Удалить агента                            |
| `GET /api/agents/:name/export`   | `apiAgentExport()`| Экспорт в .md (YAML frontmatter)          |
| `POST /api/agents/:name/test-run`| `apiAgentTestRun()`| Тестовый запуск агента через delegate     |
| `POST /api/cleanup`              | `apiCleanup()`    | worktree-gc + clean --days 7              |

**API `/api/jobs` — агрессивное упрощение (строка 70–98):**

Серверный `apiJobs()` читает ВСЕ `job.json` при каждом запросе
(синхронно, через `fs.readdirSync` + `fs.readFileSync`). Модель
обрезается до последнего сегмента через `j.model.split('/').pop()`
(строка 79). Это значит, клиент **не различает** `deepseek/deepseek-v4-flash`
и `openrouter/deepseek-v4-flash`, если разные провайдеры используют одну модель.

Фильтрация/сортировка — **только на клиенте**. Сервер возвращает весь
список. При 40+ задачах это ~40 синхронных `readFileSync` на каждый
запрос. При 400+ — станет заметно.

**API `/api/stats` — полный скан каждый раз (строка 123–173):**

Снова читает все `job.json`, фильтрует `status != 'pending'`, строит
агрегаты по моделям, дням и «capability» (прокси через `j.worktree`).

**API `/api/agents` — тоже скан + подсчёт running (строка 304–337):**

При формировании списка агентов для каждого агента **сканирует все jobs**
для подсчёта `running` (строки 312–316). O(N_agents × N_jobs).

**Ключевой баг-фикс `6bc683f` (подробно):**

Проблема: сразу после введения автообновления (коммит `154ce43`),
`setInterval` дёргал `routes[tab]()` независимо от состояния редактора
агента. Если пользователь открыл редактор на вкладке Settings,
через 5 секунд `loadSettings()` вызывал `$('#main').innerHTML = h`,
где `h` включал скрытый `#agent-editor` с `display:none`. **Редактор
сбрасывался** — пользователь терял несохранённые изменения.

Решение: перед вызовом `routes[tab]()` проверять, открыт ли редактор
(`$('#agent-editor').style.display !== 'none'`), и если да —
пропускать обновление вкладки Settings.

Это наглядно демонстрирует главную архитектурную проблему: **polling +
full re-render = постоянная борьба с потерей состояния UI**.

## 2. Сильные и слабые места (с указанием строк)

### Сильные стороны

| Аспект               | Где                                         | Комментарий                                 |
|---------------------|----------------------------------------------|---------------------------------------------|
| Ноль зависимостей    | `lib/dashboard.js` — только `http`, `fs`, `path`, `child_process` | Запускается везде, где есть Node |
| Inline-стили + system-ui | `lib/dashboard.html:8-97`               | Только системные шрифты, ни одного внешнего ресурса |
| Аккуратный роутинг | `lib/dashboard.html:544-548` (routes), `lib/dashboard.js:464-521` (URL dispatch) | Простая функция по имени вкладки |
| Escape всего вывода  | `lib/dashboard.html:138` (`esc()`)          | XSS через `innerHTML` под контролем          |
| Dark mode            | `lib/dashboard.html:14-21`, `.status` в тёмной теме | Поддержка `prefers-color-scheme` |
| Сохранение сортировки| `lib/dashboard.html:156-157` (`sortField`, `sortDir`) | Переживает перерисовку |

### Слабые места (с точки зрения интерактивности)

#### A. Задержка обновления до 5 секунд

- `lib/dashboard.html:642-649` — `setInterval(..., 5000)`. Если задача только
  что запустилась, её статус `running` не появится до 5 секунд. Наоборот —
  завершившаяся задача может оставаться в статусе `running` лишние 4 секунды.
- Особенно заметно на вкладке Статистика — накопительные метрики отстают.

#### B. Полная перерисовка DOM теряет состояние UI

- `lib/dashboard.html:223` — `$('#main').innerHTML = h` для таблицы задач.
  **Что теряется:**
  1. **Позиция скролла** — таблица после `innerHTML = h` сбрасывает скролл
     наверх. При частых обновлениях (5с) и длинной таблице это делает просмотр
     неудобным.
  2. **Активная строка** — после перерисовки никакая строка не выделена.
  3. **Фильтры теряют фокус** — `<input id="filter-search">` заново создаётся
     в строке `lib/dashboard.html:186-197`, и даже если `value` восстанавливается
     через атрибут, фокус клавиатуры теряется.
  4. **Состояние чекбоксов/раскрытых секций** (если появятся в будущем).

- `lib/dashboard.html:326` — `$('#main').innerHTML = h` для статистики.
  Аналогично.

- `lib/dashboard.html:393` — `$('#main').innerHTML = h` для агентов.
  + специальный guard для редактора агента (строка 645–647), что является
  хрупким ad-hoc решением, а не архитектурным.

#### C. Нет live-логов

- `lib/dashboard.js:118-121` — результат (`result.md`) и логи
  (`stderrTail`, `verifyLogTail`) читаются **разово при открытии detail-панели**
  и не обновляются. Если задача ещё выполняется, пользователь не видит
  прогресса — нужно закрыть и заново открыть detail.

- API для этого технически готово (`/api/jobs/:id/result`, `/api/jobs/:id/stderr`
  отдают содержимое файлов), но клиент их **не использует для автообновления**.

#### D. Сервер читает всё синхронно на каждый запрос

- `lib/dashboard.js:72-98` — `apiJobs()` делает `readdirSync` + N×`readFileSync`
  при КАЖДОМ запросе. Блокирует event loop на время чтения.
- `lib/dashboard.js:125-128` — `apiStats()` делает то же самое.
- `lib/dashboard.js:312-316` — `apiAgents()` сканирует все jobs для подсчёта
  `running`.

#### E. Схлопывание моделей разных провайдеров

- `lib/dashboard.js:79` — `j.model.split('/').pop()` теряет провайдера.
  `deepseek/deepseek-v4-flash` и `openrouter/deepseek-v4-flash` в таблице
  и фильтре выглядят одинаково.

#### F. Отсутствие обработки ошибок сети

- `lib/dashboard.html:125-129` — `get()` бросает исключение при неудачном fetch.
  Но ни `loadJobs()`, ни `renderJobs()`, ни `setInterval` не ловят ошибки.
  Если сервер упал — дашборд молча показывает старые данные (из кеша
  `jobsCache`), пользователь не знает, что данные устарели.

#### G. Индикатор соединения статичен

- `lib/dashboard.html:108` — `<span id="conn">●</span>` (зелёный кружок).
  Нигде не обновляется. Не отражает реальный статус соединения.

### Конкретные шаги (S/M/L — сложность в контексте текущего кода)

#### Шаг 1. [S] Инкрементальный рендер таблицы задач (без потери скролла)

**Проблема:** `$('#main').innerHTML = h` сбрасывает скролл.

**Решение:** Перейти на рендер через `document.createElement`/DOM API
для строк `<tbody>`. Вместо пересоздания всей таблицы:
1. Сравнить старый `jobsCache` с новым по `j.id`.
2. Добавить новые строки, обновить изменившиеся, удалить исчезнувшие.
3. Не трогать `#filter-status`, `#filter-model`, `#filter-search` —
   оставить их в DOM навсегда, только слушать события.
4. Сохранять позицию скролла до обновления и восстанавливать после.

**Файлы:** `lib/dashboard.html` (renderJobs, строки 164–224).

**Сложность:** S — заменить один `innerHTML` на ~10 DOM-операций.

---

#### Шаг 2. [S] Замена polling на Server-Sent Events (SSE)

**Проблема:** 5-секундный интервал + полная перезагрузка всех данных.

**Решение:** Вместо WebSocket (идея из `ideas.md`, оценена как L из-за
полной переработки сервера) — использовать **SSE** (EventSource API,
работает поверх HTTP, встроен в браузер):

1. Сервер: добавить endpoint `GET /api/events` с заголовком
   `Content-Type: text/event-stream`. При изменении job.json (можно
   отслеживать через `fs.watch` или просто периодически сравнивать mtime)
   — слать событие `job-update`.
2. Клиент: `new EventSource('/api/events')` вместо `setInterval`.
   `onmessage` → обновить только изменившиеся строки (п.1).

**Сложность:** S (для SSE). Почему не WebSocket: SSE проще —
однонаправленный канал сервер→клиент, не требует библиотеки,
автоматический reconnect в браузере. Достаточно для уведомлений
об изменениях. Полноценный WebSocket (L) нужен только если понадобится
двусторонняя real-time коммуникация.

**Файлы:** новый endpoint в `lib/dashboard.js:462` (createServer), замена
`setInterval` в `lib/dashboard.html:642-649`.

---

#### Шаг 3. [S] Индикатор реального статуса соединения

**Текущее состояние:** `#conn` — статичный зелёный кружок, не обновляется.

**Решение:**
1. При каждом fetch — установить зелёный.
2. При ошибке — красный.
3. При внедрении SSE (шаг 2) — `EventSource` имеет встроенные события
   `open`/`error`, можно завязаться на них.
4. Добавить текст «обновлено N секунд назад» рядом с индикатором.

**Файл:** `lib/dashboard.html:108` (HTML), `lib/dashboard.html:125-129` (get).

**Сложность:** S.

---

#### Шаг 4. [S] Live tail логов в detail-панели

**Проблема:** detail-панель (`openDetail()`, строка 228–266) загружает
логи один раз и не обновляет.

**Решение:**
1. В `openDetail()` для задач в статусе `running` запустить SSE-подписку
   на `/api/jobs/<id>/events` (или polling с интервалом 2с только для
   этой задачи).
2. Обновлять блоки `<pre>` (resultMd, stderrTail) без перерисовки всей
   панели — через `textContent` напрямую.
3. При переходе в терминальный статус — остановить подписку.

**Сложность:** S (зависит от шага 2 — если SSE уже есть, тривиально).

**Файлы:** `lib/dashboard.html:228-266` (openDetail), новый endpoint в
`lib/dashboard.js`.

#### Шаг 5. [S] In-memory кеш на сервере

**Проблема:** `apiJobs()` читает все `job.json` синхронно при каждом запросе
(строки 72–98), `apiStats()` — то же самое (строки 125–128), `apiAgents()`
сканирует jobs для подсчёта running (строки 312–316).

**Решение:**
1. Кешировать результат `apiJobs()` в оперативной памяти.
2. Инвалидировать кеш по mtime файлов (сравнивать `Date.now()` с последним
   чтением + проверять `fs.statSync` только на изменившиеся файлы) или по
   SSE-событиям.
3. Для `apiStats()` и `apiAgents()` — агрегаты тоже можно кешировать,
   перестраивая при изменении любого job.json.
4. Или проще: `setInterval` на сервере раз в 2 секунды перечитывает
   изменившиеся файлы и обновляет общий кеш; все API-хендлеры читают
   из кеша мгновенно.

**Сложность:** S-M. Простой вариант с `setInterval` на сервере — S.

**Файлы:** `lib/dashboard.js:70-98`, `123-173`, `304-337`.

**Решение:** Передавать полное `j.model` в API, а клиент пусть сам решает,

**Сложность:** S.

**Файлы:** `lib/dashboard.js:79`, `lib/dashboard.html:212` (отображение).

#### Шаг 7. [S] Удаление и kill задачи из UI

**Идеи из `ideas.md`:** «Кнопка удалить задачу» и «Кнопка убить задачу».

**Сложность:** S.

#### Шаг 8. [M] Пагинация на сервере и клиенте

**Идея из `ideas.md`:** `?limit=50&offset=0`.

**Решение:**
1. Сервер: `apiJobs()` принимает query-параметры, возвращает общее
   количество и срез.
2. Клиент: кнопки «← Назад / Вперёд →» или бесконечный скролл.
3. Фильтрация остаётся на клиенте (по загруженной странице) или
   переносится на сервер (лучше — тогда пагинация работает вместе
   с фильтрацией).

**Сложность:** M — нужно согласовать фильтрацию и пагинацию, решить,

#### Шаг 10. [M] Event-driven архитектура клиента

**Текущее состояние:** Функции вкладок напрямую дёргают `renderJobs()`,
`renderFilters()` и т.д. При добавлении нового источника обновлений
(SSE вместо polling) придётся менять все места вызова.

**Решение:**
1. Простая pub/sub шина: `const bus = { _events: {}, on(e, fn) { ... }, emit(e, data) { ... } }`.
2. `bus.on('jobs-updated', renderJobs)` — функция рендера подписывается.
3. `bus.emit('jobs-updated', newData)` — вызывается из polling / SSE / ручного обновления.

**Сложность:** M — требует рефакторинга всех вызовов, но даёт гибкость.

**Файлы:** весь `lib/dashboard.html`, но особенно строки 155–224, 544–548, 642–649.

## 5. Резюме

Дашборд `.ai` — минималистичный, самодостаточный SPA на чистом JavaScript
без внешних зависимостей. Сервер — голый `http.createServer()`, клиент —
один HTML-файл с inline-стилями и скриптами. Архитектура простая и
прозрачная: три вкладки, каждая тянет свой JSON-эндпоинт, перерисовывает
`innerHTML` раз в 5 секунд.

**Главный архитектурный тормоз интерактивности:** сочетание polling
(задержка до 5 с) + полная перерисовка DOM (потеря скролла, фокуса,
состояния UI). Оба лечатся в рамках vanilla JS:

1. **SSE вместо polling** (~20 строк на сервере + 10 строк на клиенте) —
   мгновенные обновления без постоянного опроса.
2. **Инкрементальный рендер** вместо `innerHTML = h` — сохраняет скролл,
   фокус фильтров, выделение строк.
3. **Live tail логов** в detail-панели — подписка на обновления файлов
   для выполняющихся задач.

Все предложенные улучшения укладываются в подход «ноль зависимостей,
ванильный JS». Ни один шаг не требует фреймворка — только рефакторинг
существующего кода в сторону событийной модели и DOM-диффинга на уровне
строк таблицы.

Путь к отчёту: `research/dashboard-codebase-audit.md`
